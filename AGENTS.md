# Project-local maintenance rules

- Current build policy (2026-11-09): personal builds run locally by default. This supersedes earlier cloud-only and local-cache-preservation instructions; historical validation records remain evidence for their recorded commits.
- Changes that affect the same-account connection retry must preserve the fixed `CT-CONNECT-RETRY-001` v1.0 contract in `docs/local-patches/same-account-connect-retry.md`. Before handing off a transport change, run `scripts/verify-native-connect-retry.sh` locally with the existing toolchain or in a manually selected cloud run; after an upstream merge, also perform the documented duplicate-retry review.
- The API service follows upstream Rust Native only. Keep the setup-only retry contract in `docs/local-patches/native-connect-retry.md`; the retired Go reference remains in Git history, not as a bundled engine or build dependency.
- The maintained additions are Native connection setup retry, Native Credits admission, the local-project recovery fix in `docs/local-patches/project-recovery-large-history.md`, and local/manual-cloud build and publication tooling. Project recovery must not skip solely because the profile has more than 2048 threads or a state JSON/backup larger than 2 MB; preserve deadlines, concurrent-change checks and the existing data boundaries. Use upstream Auto Reset, provider model configuration, tool protocols, continuation and quota-reserve implementations. Do not reintroduce retired Go, Reset compatibility, provider metadata/manual-policy extensions, or a second plaintext marker policy. Credits must still be enforced for the actual credential identity.
- Use `npm run build:app` or `npm run build:app:local` for the personal local App. Start with checks targeted to the changed behavior, fix failures locally, and reuse project build outputs during that iteration. Do not repeatedly dispatch a full cloud build to diagnose each local failure. `npm run build:app:cloud` and the Cloud Build workflow UI remain explicit manual alternatives.
- Cloud Build runs only by `workflow_dispatch`; pushes and pull requests must not automatically start its full build. Use standard GitHub-hosted runners only, with no paid/larger runners or paid build services. Formal `v*` releases retain their existing signed multi-platform release workflow and verification gate.
- Personal builds select only `macos-x86_64`, matching this Intel Mac. Keep every existing platform supported: manual Cloud Build accepts one platform or `all`, and fork users can choose their own platform. Keep the Rust Native engine and upstream application features; do not bundle Go.
- Reuse cloud caches by platform/architecture and dependency inputs when cloud builds are selected. Run the frontend typecheck once per App build. Give cloud intermediate artifacts short retention and replace rolling platform downloads instead of accumulating duplicates. Never cache or upload account profiles, runtime configuration, tokens, logs, signing keys, or other private data.
- The local builder only builds; it must not install, stop or launch the App. Once its output passes version, architecture and signature verification, remove this project's `target/`, `node_modules/`, `dist/` and this build's scratch, retaining the verified App in `.local-app-output/`. Keep the previously installed App until its replacement has been installed and confirmed to launch, then remove the old App and duplicate artifacts. Source, Git history/remotes, all runtime account/configuration/session data and shared toolchains must remain. Failed builds may keep project diagnostics and caches for targeted repair. Do not create a full backup or delete shared toolchains/caches or unrelated work.
- Keep `origin` pointed at the user's public fork and `upstream` at the canonical project. Merge upstream changes into the public branch without replacing source wholesale or discarding patch history. Follow `docs/cloud-builds.md` for local validation, optional manual cloud builds, installation, cleanup and public-fork synchronization.
